# ハッシュチェーンとマークル木

[English](concepts.md)

deedlog が記録を「こっそり書き換えられない」ようにしている 2 つの仕組みを、予備知識なしで読めるように説明します。
正確な定義は[仕様](../spec/)にあります。

## まず、ハッシュ

ハッシュは、データから計算する短い「指紋」です。deedlog は SHA-256 を使い、どんな大きさのデータからも 64 桁の英数字が得られます。

- 同じデータからは、いつ誰が計算しても同じ指紋が出る。
- 1 文字でも変えると、まったく別の指紋になる。
- 指紋から元のデータは分からず、同じ指紋になる別のデータを作ることも事実上できない。

つまり、指紋を控えておけば、後で「データが 1 文字も変わっていない」ことを確かめられます。
deedlog の記録に証拠そのものではなく証拠の指紋だけを入れるのも、この性質を使っています。

## ハッシュチェーン：前のページの指紋を書き写す

台帳の各ページの冒頭に、直前のページの指紋を書き写していくところを想像してください。

```
 記録0            記録1            記録2            記録3
┌─────────┐      ┌─────────┐      ┌─────────┐      ┌─────────┐
│ 内容    │◀─────│前: 指紋0│◀─────│前: 指紋1│◀─────│前: 指紋2│
│         │      │ 内容    │      │ 内容    │      │ 内容    │
└─────────┘      └─────────┘      └─────────┘      └─────────┘
```

記録 1 を書き換えると記録 1 の指紋が変わり、記録 2 に書き写した「前: 指紋1」と合わなくなります。
記録を抜いたり、間に差し込んだり、順番を入れ替えたりしても、同じように食い違いが出ます。

書き換えた人が、それ以降の記録をすべて作り直せば、食い違いは消せます。
ただしそのとき、最後の記録の指紋も変わります。最後の指紋を誰か別の人が控えていれば、作り直しは見破れます。
次に説明するチェックポイントは、この「誰か別の人が控えておく」を仕組みにしたものです。

ハッシュチェーンには弱点が 1 つあります。ある 1 件が台帳に入っていることを確かめるには、先頭から全件をたどる必要があります。
100 万件の台帳なら 100 万件です。

## マークル木：トーナメント表のように指紋をまとめる

マークル木は、記録の指紋をトーナメント表のように 2 つずつ組にして、組の指紋を計算し、それをまた組にして……と、最後に 1 つの指紋にまとめたものです。
最後の 1 つを**根**と呼びます。4 件なら次のようになります。

```
                 根
            ┌────┴────┐
          指紋AB     指紋CD
         ┌──┴──┐   ┌──┴──┐
         A     B   C     D      ← 各記録の指紋
```

根は 64 桁の英数字 1 つですが、全件の中身と順番を表しています。どれか 1 件でも変われば、根が変わります。
deedlog の**チェックポイント**は、「件数」と「根」に運営者が署名し、独立した連署サーバーが連署し、タイムスタンプ局が時刻を証明したものです。
小さな根を 1 つ固定するだけで、その時点の全件が固定されます。

マークル木には、ハッシュチェーンにない利点が 2 つあります。

**1 件が含まれていることを、少ない指紋で示せる。** 上の図で記録 C が入っていることを示すには、C のほかに「D の指紋」と「AB の指紋」の 2 つを渡せば足ります。
受け取った人は C と D から CD を、CD と AB から根を計算し、署名された根と一致するかを確かめます。
必要な指紋は、トーナメントで当たる相手の数だけです。100 万件でも 20 個ほどで、ほかの記録の中身を見せる必要もありません。
受領証を持つ人が「自分の出来事が本当に記録されている」と確かめるときに使うのが、これです（含有証明）。

**前の根から、後ろに足しただけであることを示せる。** 昨日の根と今日の根を比べて、昨日までの記録を 1 件も変えずに後ろに追加しただけであることも、少しの指紋で示せます（一貫性証明）。
連署サーバーは記録の中身を受け取らずにこれを確かめ、確かめられたときだけ連署します。
運営者が過去を書き換えたり、相手によって違う台帳を見せたりすると、連署が得られないか、矛盾する 2 つの署名済みチェックポイントが残り、それがそのまま不正の証明になります。

## deedlog での使い分け

deedlog は、同じ記録から両方を計算します。

| | ハッシュチェーン | マークル木 |
|---|---|---|
| どこにあるか | 各記録の `prev`（直前の記録の指紋） | チェックポイントの根 |
| 確かめられること | 順番どおりにつながっていて、抜けも差し込みもない | ある時点の全件がそのまま固定されている |
| 確かめ方 | 全件を手元に置いて、先頭から順にたどる | 1 件と少しの指紋だけで確かめる。全件は要らない |
| 誰が使うか | 台帳全体を持つ監査人など | 受領証を持つ本人、連署サーバー |

チェーンだけでは「最後の指紋を誰が控えるか」が決まらず、木だけでは記録を手にした人が前後のつながりをその場で確かめられません。
両方を組み合わせ、根を運営者以外の人たちが控えることで、記録を書き換えたり外したりすれば必ず跡が残るようにしています。

## できないこと

- 改ざんを**防ぐ**のではなく、**見破れる**ようにする仕組みです。書き換えそのものは止められませんが、隠せません。
- 最初から嘘の内容を記録することは防げません。確かめられるのは、記録した後に変わっていないことです。
- 根を運営者しか持っていなければ、作り直しは見破れません。連署サーバー、タイムスタンプ、受領証は、根を運営者の手の届かない場所に置くためにあります。

詳しくは[信頼モデル](../spec/trust-model.md)を、正確な計算方法は[記録の仕様](../spec/evidence-chain.md)の §5 と[チェックポイントの仕様](../spec/checkpoint.md)の §2 を参照してください。
マークル木は RFC 9162（Certificate Transparency）と同じもので、ウェブの証明書の透明性ログでも使われています。
